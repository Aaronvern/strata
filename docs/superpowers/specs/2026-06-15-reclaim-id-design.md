# Reclaim ID — Compliance Credential Adapter Design

**Date:** 2026-06-15
**Status:** approved design, pre-implementation
**Scope decision:** Reclaim credential adapter only. Sanctions oracle, KMS key custody, and real jurisdiction policies stay as their current stubs and are documented here as go-live prerequisites. Code is structured so each can be swapped in later without redesign.

---

## 1. Goal

Add [Reclaim Protocol](https://reclaimprotocol.org) zkTLS proof verification as a real, production-shaped credential source for the Strata Compliance Agent's deposit gate. This is the documented "v2" credential adapter that `agents/compliance/docs/strategy-v1.md` always reserved ("v2 swaps in zkPass or Privado ID") — Reclaim fills that slot.

A user proves a real-world fact (KYC status / nationality) from an existing account via Reclaim, the Compliance Agent verifies the proof off-chain, maps it to Strata's compliance model (`kycTier` + `jurisdictionCode`), and issues the existing EIP-712 compliance receipt → soulbound NFT that gates `TrancheVault.deposit()`.

### Non-goals (explicitly out of scope)
- **On-chain trustless verification** (calling Reclaim's on-chain verifier from a `ReclaimComplianceGate`). Reclaim's published on-chain deployments do not include Mantle (chainid 5000), so this is likely blocked without Reclaim deploying there. The design preserves the on-chain proof identifier so this can be added later without schema changes.
- **Replacing the stub sanctions oracle** (`stubSanctions.ts`). Remains a documented go-live gate.
- **KMS key custody** for the receipt signer. Remains env-key based; documented go-live gate.
- **Real jurisdiction policies.** In-memory stub policies remain; documented go-live gate.
- **Any Solidity change.** `ComplianceRegistry.sol`, `TrancheVault.sol`, and the receipt schema are untouched.

---

## 2. Chosen approach

**Off-chain Reclaim credential adapter** that implements the existing `CredentialAdapter` seam in the Compliance Agent, plus a web-app proof-generation step that hands the proof to the existing `/api/v1/compliance/check` endpoint.

**Trust model:** identical to today — the Compliance Agent is the trusted off-chain verifier and receipt signer. This is the standard model for KYC/identity integrations (Persona, Sumsub, Onfido all work this way). Not trustless; acceptable and unchanged from current production posture.

### 2.1 Decisions locked (2026-06-15)

- **Surface:** existing Next.js web dApp (`apps/web`) + QR handoff to the user's phone. Reclaim proving is mobile-native (the user proves on the device logged into the exchange); no separate mobile app is built. A React Native app is explicitly deferred.
- **Target users:** global crypto-natives who already hold exchange accounts.
- **Provider:** an exchange **KYC-completion** provider (Coinbase has a published one; OKX is used in production) — "reuse the KYC you already did." Exact `providerId`/`providerVersion` chosen in the Reclaim dashboard later.
- **Mapping outputs:** `kycTier` from the proof's KYC-status field; **`jurisdictionCode` is *not* proven in this build** — it defaults to `permissionless` (→ junior-only via the existing policy table). Country-based routing (US/EU/GB) is a later config addition (a country field on the same provider, or a second proof), not code change.

## 3. Data flow

```
Browser (deposit page)                    Compliance agent (:9094)            Chain
─────────────────────                     ────────────────────────            ─────
1. connect wallet
2. GET /reclaim/config?wallet=0x…  ──────► init ReclaimProofRequest
                                           (appId+secret), set context.address=wallet
                                   ◄────── reclaimConfig JSON
3. fromJsonString → getRequestUrl
   → show QR → startSession()
4. user proves on their device → onSuccess(proof)
5. user signs DepositorAuth (EIP-712)
6. POST /api/v1/compliance/check  ───────► verifyProof(proof) → {isVerified,data}
   {wallet, credentialProof:{kind:'reclaim',                assert context.address==wallet
     proofs}, depositorAuthSig, deadline}                   profile maps extractedParameters
                                                            → {kycTier, jurisdictionCode}
                                           → sanctions(stub) → policy(stub) → route
                                           → sign receipt (EIP-712)
                                           → encrypt proof as evidence → pin Lighthouse
                                           → mint ComplianceReceipt ──────────► ComplianceRegistry
                                   ◄────── {status:'approved', permittedTranchesMask, …}
7. useComplianceReceipt refetches → deposit form unlocks
```

The proof-request config is generated by the agent (not the web app) so `RECLAIM_APP_SECRET` stays server-side with the verifier and the per-request `context.address` is set to the depositor wallet.

## 4. Components — Compliance Agent

### 4.1 `adapters/reclaimCredential.ts` (new)
Implements the existing `CredentialAdapter` interface with `provider: 'reclaim'`.

`verify(proof, wallet)`:
1. `const { isVerified, data, error } = await verifyProof(proof.proofs, { providerId, providerVersion })` — current SDK API.
2. `!isVerified` → return invalid `CredentialResult` (fail-closed).
3. Read `data[0].context` and `data[0].extractedParameters`.
4. **Wallet binding:** assert `context.address.toLowerCase() === wallet.toLowerCase()`; mismatch → invalid.
5. **Freshness:** assert `data[0].claimData.timestampS` within a configured window; stale → invalid.
6. Apply the provider profile (§4.2) → `{ kycTier, jurisdictionCode }`.
7. `credentialEvidenceHash = keccak256(canonicalProofBytes)`.
8. Return `CredentialResult { valid, kycTier, jurisdictionCode, credentialEvidenceHash, issuer, provider:'reclaim' }`.

Constructed via `createReclaimCredentialAdapter({ providerId, providerVersion, profile, now? })`. Verification does **not** need `appSecret` (only `init` does, which happens in the config endpoint).

### 4.2 `adapters/reclaimProfiles.ts` (new) — the mapping layer
Declarative profile so provider choice is config, not code. Shape:

```ts
interface ReclaimProfile {
  providerId: string;
  providerVersion: string;
  statusField: string;                       // key in extractedParameters
  statusToTier: Record<string, KycTier>;     // e.g. { verified:'basic', level2:'enhanced' }
  countryField: string;                      // key in extractedParameters
  countryToJurisdiction: Record<string,string>; // ISO → US/EU/GB/…
  declaredDefaults?: { kycTier?: KycTier; jurisdictionCode?: string };
}
```

- Mapping is **deny-by-default**: if a required field is absent and the profile declares no explicit default for it, `verify` denies. Defaults apply only where `declaredDefaults` names them.
- Ships two profiles, selected by `RECLAIM_PROFILE`:
  - **`exchange-kyc`** (the chosen real profile): `statusField` → `statusToTier` (KYC completed → `basic`; a level field → `enhanced` if the provider exposes one). **No `countryField` used in this build**; `declaredDefaults.jurisdictionCode = 'permissionless'` so a verified user routes to junior-only via the existing policy table. To enable US/EU/GB routing later, add `countryField` + `countryToJurisdiction` to this profile — config only.
  - **`demo`** (for tests / no-account dev): a reliably-available provider (e.g. GitHub/Google) with `declaredDefaults:{ kycTier:'basic', jurisdictionCode:'permissionless' }`, to exercise the full pipeline without an exchange KYC account.

### 4.3 `api/server.ts` (modify)
- Add `GET /api/v1/compliance/reclaim/config?wallet=0x…` → `ReclaimProofRequest.init(appId, appSecret, providerId)`, set context address = wallet, return `toJsonString()`. CORS already enabled.
- Extend `/api/v1/compliance/check` body validation to accept the reclaim `credentialProof` variant (§4.5).

### 4.4 `gate.ts` / `config.ts` (modify)
- `config.ts`: add `CREDENTIAL_PROVIDER` (enum `stub|reclaim`, default `stub`), `RECLAIM_APP_ID`, `RECLAIM_APP_SECRET`, `RECLAIM_PROVIDER_ID`, `RECLAIM_PROVIDER_VERSION`, `RECLAIM_PROFILE`, `RECLAIM_PROOF_MAX_AGE_SEC`. All optional unless `CREDENTIAL_PROVIDER=reclaim` (then required ones are validated).
- `gate.ts`: build the reclaim adapter when configured, else the stub adapter.

### 4.5 Discriminated-union credential input (`adapters/credential.ts`, `types.ts`)
The single structural edit. `credentialProof` becomes a tagged union:

```ts
type CredentialProofInput =
  | ({ kind: 'stub' } & EIP712CredentialProof)   // existing struct
  | { kind: 'reclaim'; proofs: ReclaimProofArray; providerVersion?: string };
```

- Add `'reclaim'` to `CredentialProvider` zod enum (`types.ts:10`).
- `CredentialAdapter.verify` param generalized to `CredentialProofInput`; each adapter narrows by `kind`.
- **Back-compat:** untagged input is treated as `{ kind:'stub' }`, so existing stub path and tests stay green.
- `gateOrchestrator.ts` routes to the adapter matching the input `kind` / configured provider.

## 5. Components — Web app (Next.js, `apps/web`)

### 5.1 `components/app/ReclaimVerify.tsx` (new)
Shown when wallet connected but `useComplianceReceipt` returns `tokenId === 0` and reclaim mode is enabled. Flow: fetch config from agent → `ReclaimProofRequest.fromJsonString` → `getRequestUrl` → render QR (`react-qr-code`) → `startSession({ onSuccess, onError })`. On `onSuccess(proof)`: prompt the `DepositorAuth` EIP-712 signature, then `checkCompliance({ wallet, credentialProof:{kind:'reclaim',proofs}, depositorAuthSignature, deadline })`. On `approved`/`existing`, trigger `useComplianceReceipt` refetch.

### 5.2 `lib/compliance.ts` (modify)
Add the reclaim `credentialProof` variant to `ComplianceCheckRequest` and a `fetchReclaimConfig(wallet)` helper hitting the agent endpoint.

### 5.3 `DepositGate.tsx` / `DepositView.tsx` (modify)

### 5.4 Dependencies
`apps/web`: add `@reclaimprotocol/js-sdk`, `react-qr-code`. `agents/compliance`: add `@reclaimprotocol/js-sdk`.

## 6. Security & wallet binding

Two independent, fail-closed layers:
1. **Cryptographic** — Reclaim `context.address` (signed inside the proof) must equal the depositor wallet.
2. **Consent** — the existing `DepositorAuth` EIP-712 message signed by that wallet (already in `gateOrchestrator` step 3).

Plus proof freshness (`timestampS` window) and the existing receipt idempotency / nonce handling. Binding to `context.address` prevents replaying another user's proof against a different wallet.

---

## 7. Error handling (matches existing fail-closed posture)

| Condition | Outcome |
|---|---|
| `verifyProof` returns `!isVerified` or throws | deny `credential-invalid` |
| `context.address` ≠ depositor wallet | deny `credential-invalid` |
| proof older than `RECLAIM_PROOF_MAX_AGE_SEC` | deny `credential-invalid` |
| required profile field missing, no declared default | deny `credential-invalid` |
| Reclaim service unreachable | deny `internal-error` |

All routed through the existing typed-denial path; no optimistic defaulting.

---

## 8. Receipt & evidence (reuses existing schema)

The Reclaim proof JSON is the evidence: encrypted with the existing AES-256-GCM `evidence.ts` → pinned to Lighthouse → CID stored in the receipt's existing `zkReceiptCid`. `credentialEvidenceHash = keccak256(canonicalProofBytes)`; `credentialProvider: 'reclaim'`. The on-chain proof `identifier` is preserved in the evidence so a future trustless on-chain verifier can re-check it without any schema change.

## 11. Go-live prerequisites (out of scope here, must be done before real money)

1. **Real sanctions oracle** — replace `stubSanctions.ts` with Chainalysis/TRM/Elliptic (needs vendor key). AML liability otherwise.
2. **KMS key custody** — move `COMPLIANCE_PRIVATE_KEY` to a KMS signer (Turnkey/AWS KMS); the receipt signature is the protocol's legal claim.
3. **Real jurisdiction policies** — legally-authored, multisig-published policies replacing the in-memory stub.
4. **Reclaim production plan** — paid Reclaim app; chosen real provider with a verified `providerId`/`providerVersion`; provider maintenance plan (zkTLS providers break when source sites change).
5. **Legal layer** — licensing, entity structure, counsel sign-off on the jurisdiction→tranche rules. Not a code deliverable.

## 12. To verify at implementation time (do not assume)

The exact installed `@reclaimprotocol/js-sdk` version's API for:
- Setting context / wallet address on the proof request (`addContext` / `setSignature` / equivalent).
- Whether `startSession` returns the proof purely via `onSuccess` or requires a public callback URL. If a callback is required, the agent exposes `/api/v1/compliance/reclaim/callback` (publicly reachable in real deploy) storing the proof by session id, and the browser polls. The design works either way; confirm against the pinned version before coding the web flow.
